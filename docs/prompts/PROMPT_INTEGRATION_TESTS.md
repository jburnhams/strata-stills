# Task: add thorough integration tests to strata-stills (one PR, then stop)

You are a coding agent new to this repo. Find a coherent slice of **CLI, pipeline or server behaviour that has no integration test**, cover it with thorough, best-practice tests on small synthetic photos, and extend and refactor the shared fixtures as you go. Open **one PR**, drive CI to green, then stop. This prompt is run many times: each run continues from the state the last one left, so choose work from the *current* ledger and leave it up to date.

## Unattended operation (read first)

You run without a human: nobody will answer questions, approve a plan or review before you open the PR. Never ask for clarification or confirmation, never stop to wait for input, and never end your turn with a question. When something is ambiguous, pick the most reasonable option, note the decision in the PR description and carry on. Specifically:

- If the branch name, the slice, a convention or a tool is unclear, decide using this prompt, `AGENTS.md`, the READMEs and the sister project `../strata-360`; record the choice under "Decisions" in the PR.
- If a command fails or a tool is missing (no GPU, no node, no network access to a registry), work around it or rely on CI as the runner; do not stop. If you truly cannot make progress on part of the slice, drop that part, list it under "Not done" in the PR, and finish the rest.
- If you find a bug or something out of scope, record it under "Findings" in the PR (as an xfail or `it.fails` where this prompt says so); don't ask whether to fix it.
- Whenever you have made changes, finish by opening the PR (or, if one already exists for your branch, pushing to it) and driving CI to green as described below; a PR with a clear "Not done" list beats no PR. If the stop condition applies and there is nothing to change, open no PR. Don't merge, and don't wait for a reviewer.

Read **`tests/README.md`** (shared commands, hermetic setup, ownership rules) and **`tests/integration/README.md`** (fixtures, conventions, coverage table, known issues) in full. **This task runs in parallel with the unit-test and web-test tasks on other branches, so obey the ownership table in `tests/README.md`**: you may edit `tests/integration/**`, new `tests/utils/integration_<topic>.py` files, and `tests/integration/README.md`. Don't touch `tests/unit/**`, `tests/conftest.py`, the other `tests/utils/` files (including `photos.py`: add your own builders in an `integration_*.py` helper or `tests/integration/conftest.py`), `tests/README.md`, `tests/unit/README.md`, `pyproject.toml` (integration coverage is informational), `requirements-test.txt` (unless a new test dependency is unavoidable, and say so in the PR), the workflows or `web/`. Then read `tests/conftest.py`, `tests/integration/conftest.py`, `tests/utils/photos.py` (what the synthetic shoot is and how it's built) and the worked examples: `tests/integration/test_cli.py`, `test_pipeline_end_to_end.py`, `test_server_api.py`. Commands from the repo root: `pytest tests/integration -n auto` (about 20 s), `pytest tests/integration/test_x.py -k name`, `pytest tests/integration -p randomly --randomly-seed=N` (reproduce an order), `pytest tests/integration --durations=15`, `ruff check src tests`.
5. **GitHub Actions is the source of truth.** `integration.yml` runs this suite on Linux, macOS and Windows (all blocking), plus the web component tests, and weekly. `unit.yml` runs lint and the unit suite. Code must be cross-platform (Windows first): build paths with `os.path`/`pathlib`, never assume symlinks or POSIX permissions (skip with a reason). ## 1. Choose the slice (data-driven, so reruns don't collide)

1. Open the coverage table in `tests/integration/README.md` and cross-check it against a fresh run: `pytest tests/integration -n auto --cov --cov-fail-under=0 --cov-report=term-missing` (informational), or the latest CI log. Look for behaviour that unit tests can't reach but integration can: `cli.py` commands and exit codes, `pipeline.py` end to end (each stage, presets, `auto` rules, resume and cached results, a changed setting invalidating exactly the stages after it), `export.py`/`fullres.py` output files, `ingest.py` over a real folder, `projects.py` on disk, and the `server/app.py` endpoints that need real files (thumbnails, previews, generate and its job control, downloads, the path security boundary).
2. Check what's in flight: `git log --oneline -20`, `git branch -a`, open PRs (GitHub MCP tools). Don't pick what another branch or PR covers; check `tests/unit/README.md` so you don't duplicate unit coverage. If an earlier run's PR for the same slice is still open, continue on it.
3. Pick **one cohesive slice**: aim for 15-30 tests across 1-3 files. Prefer behaviour users depend on (resumable and cached results, stale handling, error reporting, **originals untouched**: after any command the source folder must be byte-identical, with no new, renamed or deleted file), things that broke before (see `git log --grep fix`), and boundaries: an empty folder, an unsupported or zero-byte or truncated file, a JPEG without EXIF/XMP, a DNG without a profile, a folder with only a video, non-ASCII or very long paths, two projects over the same source, a picture too big for the tile limit.
4. State the chosen slice and why at the top of the PR description.
5. **Stop condition:** if the table shows nothing valuable left that can be tested without models or special hardware, change nothing, open no PR, say so in your final message, and don't invent work.

## 2. Reuse and extend the shared fixtures (don't bypass them)

- Use `cli` (in process) for commands, `cli_subprocess` only for entry-point and isolation tests, `shoot` for photos, `project` for a project over it, `client` for the HTTP API over that project. Never re-run a pipeline stage in a test just to obtain its output; only run it in the test that is *about* running it. The AI denoise is off (`STRATASTILLS_AI=0`); a test of the learned path fakes the model.
- If you need a different shared state, add a fixture instead of building it inside tests: a session-scoped template of a developed project copied per test (instant), a shoot with a specific defect (corrupt JPEG, no metadata, missing DNG), a parameter on a builder wrapper in `tests/utils/integration_<topic>.py`. Never mutate a shared template in place.
- When you touch an older file, convert it to the house style: pytest functions/classes with plain `assert`, fixtures instead of `tempfile`, no `sys.path` hacks, no `__main__` runners, `monkeypatch` instead of module-global assignments. Preserve every assertion's meaning. If a test is pure logic, leave it and list it under "Known issues" in `tests/integration/README.md` as a candidate for `tests/unit/`. Don't convert files outside your slice.
- Add a test dependency only for a clear reason, put it in `requirements-test.txt`, and say why in the PR.

## 3. How to write the tests

- Assert on **artifacts**, not just printed text: the JSON a command wrote or returned (exact fields and values), the files a stage produced (dimensions, bit depth, colour space or ICC, EXIF carried over, file name), the HTTP status and body and the files an endpoint created, exit codes and the error message on failure (`cli(..., check=False)`). Compare pixels with tolerances (float32 and different BLAS builds differ slightly), never exact bytes of an encoder's output.
- Cover for each behaviour: happy path; idempotent re-run (nothing redone, the cached result reused); a changed setting or a bumped stage VERSION invalidating exactly what it should (cache keys); missing and malformed inputs; partial failure (one picture bad, the others still processed and the failure reported); cancellation and resume where applicable; the security boundary for server paths (`..`, absolute paths, a symlink out of the roots where the platform allows) and downloads.
- Keep each test under ~10 s; share expensive state through fixtures; no `time.sleep` (poll a job with a deadline helper); no fixed ports (use `TestClient`); no dependence on the working directory or on test order. The suite must pass alone, in random order (`pytest-randomly` runs by default) and in parallel (`-n auto`).
- Don't change `src/` behaviour in a test-only PR. Allowed: a tiny testability change (a parameter with a default), called out in the PR. A bug found: write the test for the *correct* behaviour with `@pytest.mark.xfail(strict=True, reason='...')` and list it under "Findings". Never skip, delete or weaken an existing test.

## 4. Update the notes

In `tests/integration/README.md`, update the coverage table for every area your tests exercise (integration coverage, informational, which tests, what remains), record new fixtures and gotchas under "Fixtures" and "Conventions", and move anything you found slow or mislabelled into "Known issues" (or fix it if it's in your slice). Don't edit `tests/README.md` or `tests/unit/README.md`.

## 5. Verify locally

`ruff check src tests`; `pytest tests/integration -n auto` and again serially with a few `--randomly-seed` values; `pytest tests/unit -q` if you touched shared fixtures; `--durations=15` to check nothing you added is slow (>10 s: share state or shrink the picture). Mutation spot-check: break the source (flip a condition) for 2-3 representative tests, confirm they fail, then revert. Re-read your diff adversarially for tests that would still pass if the code were broken.

## 6. Branch, PR, and drive CI to green

- Use the branch name the environment gives you (otherwise `test/integration-<slice>` off the latest default branch). Make small logical commits (fixtures/helpers -> tests -> notes). Push with `git push -u origin <branch>`.
- Open **one PR** (follow its PR template if the repo has one) as soon as the first meaningful commit is pushed; keep it a draft until CI is green if you can.
- Loop until CI is green on the latest head commit:
  1. Read results with the GitHub MCP tools (`actions_list`, `actions_get`, `get_job_logs`); the durations output in the integration job shows what's slow.
  2. If red, reproduce, root-cause, push a minimal fix, repeat. macOS/Windows-only failures are usually path separators, line endings, open files that can't be deleted on Windows, long paths, timing, or numeric tolerance: fix the test (or skip with a precise reason only when the platform genuinely can't do it).
  3. If a failure is clearly not yours (the web jobs, or an infrastructure error), say so in one PR comment with the evidence and re-run at most once. Never mask a flake, skip tests to get green, or push an empty commit to retrigger CI.
- The PR description must include: the slice and why (and what's left); tests added and files converted; new fixtures/helpers; suite duration before -> after (from the CI log) and the slowest new tests; "Findings" (bugs as xfails, slow or mislabelled tests, any `src/` change).
- Finish by stating the CI status on the head commit, the PR link, and what remains. Don't merge. Don't start a second slice. If review comments or CI events arrive on your PR, handle them as part of this same PR.
