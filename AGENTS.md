# Repository Guidelines

Sister project of `../strata-360` (video): same structure, libraries, build and conventions, applied to still images. When in doubt, do what strata-360 does; port code from it rather than rewriting it, and note ports in `NOTICE`/`docs/progress.md`.

- Python application code lives in `src/stratastills/`; the React web app lives in `web/src/` and build into `src/stratastills/server/static/`, as in strata-360.
- Python tests live under `tests/`: `tests/unit/` (fast, isolated, synthetic data; no models, no real photos), `tests/integration/` (CLI/server on synthetic photos), `tests/utils/` (shared helpers). Real photos (`shoots/`, the drone folders on `\\Server\Drone`) are never required by tests and never committed.
- Commands (from the repo root, with `.venv` active or via `./stratastills` / `stratastills.cmd`):
  - `pip install -r requirements-test.txt` is enough for the test suites.
  - `pytest tests/unit --cov` (coverage floor `fail_under` in `pyproject.toml`; it only ratchets up), `pytest tests/integration -n auto` (the CLI, pipelines and HTTP API on synthetic photos from `tests/utils/photos.py`), `ruff check src tests`. Test layout, fixtures, ownership: `tests/README.md`.
  - CI is `.github/workflows/unit.yml` (lint, unit tests with coverage on Linux 3.11-3.13, macOS and Windows; web typecheck, coverage gate, build) and `integration.yml` (integration tests on three OSes, web component tests, weekly). `scripts/setup_env.ps1` / `setup_env.sh` build the environment from scratch.
  - `./stratastills doctor` checks the environment; `./stratastills scan <folder> [--info]` lists the shots in a folder.
- Cross-platform, Windows (NVIDIA GPU) first. OS differences go in one module (`oslib.py`, to be ported from strata-360 when needed); GPU/encoder choice in `hw.py`.
- Originals are read-only: nothing here ever writes into, renames or deletes files in a source folder. Output goes to a separate project/output folder.
- Style: dense, comment-the-why, long lines are fine (ruff line-length 400), pytest style tests.
- Docs live in `docs/`: `overview.md` (design brief), `implementation-plan.md` (what to build next, in order), `progress.md` (log of findings and decisions), `prompts/` (test-writing prompts: backend unit, integration, web).
- Web (from `web/`): `npm install`, `npm run dev` (proxies /api to `./stratastills serve` on 8361), `npm run build` (writes into `src/stratastills/server/static/`, which `serve` serves), `npm run typecheck`, `npm run test:unit` (node), `npm run test:integration` (jsdom + msw: every endpoint the app calls needs a handler in `web/tests/utils/server.ts`).
- App shape: projects -> source folders -> contents (items) -> item (variants: pick the primary; transforms: original, levelled ...). Transforms live in `src/stratastills/transforms.py` (each has a VERSION in its cache key) and the frontend lists them in `web/src/api.ts` TRANSFORMS: add to both.
- Pipelines: `src/stratastills/pipeline.py` (stages, presets, generate, rules). A new stage needs an entry in `ORDER`, `PARAMS`, `version()` and a runner; its settings are part of the key of what it makes, so bump its version when its result changes. Generated pictures are variants of an item (`projects.generated_variants`); the web Generate panel shows the stage settings of the pipeline that will run from the server's `generate/check`, so the UI never duplicates the preset logic.
- GPU: `src/stratastills/gpu.py` is the pixel pipeline in PyTorch for NVIDIA CUDA and Apple MPS; with neither, the NumPy/OpenCV code in `develop.py` and `detail.py` runs (STRATASTILLS_GPU=0 forces that, STRATASTILLS_DEVICE=cuda|mps|cpu forces a device). The CPU code is the REFERENCE: every function in gpu.py has a CPU original and `tests/unit/test_gpu.py` holds them to the same answer on every device (torch-CPU always, CUDA and MPS where present), so change the recipe in develop.py/detail.py first and mirror it in gpu.py. Operations a backend lacks must be probed and have a fallback (see `cubic_ok`). Only float32 (MPS has no float64).
- Memory: a picture too big for the card is developed in tiles (`gpu_tiled.py`; the CPU path has `cpu_tiled.py`), a batch goes through in tiles when the card cannot hold that many whole pictures (`gpu.batch`), and the tile size follows the memory there is (`gpu.tile_size`, `resources.cpu_tile`). Tuning variables: `STRATASTILLS_GPU`, `_DEVICE`, `_GPU_SLOTS`, `_MAX_PIXELS`, `_TILE`; tests clear them.
- Candidate photos: `candidates/` (gitignored) holds real photos copied from the shoots for working on a camera's parity (`scripts/copy_candidates.py docs/a7c_candidates.json <shoot folder> [--add stems]`); the numbers to beat are in `docs/a7c_candidates.json` (`scripts/parity_jpeg.py candidates/a7c --ev match --candidates docs/a7c_candidates.json`, `--accept` after a change judged better). Tests never need them.
- DJI candidates: docs/dji_candidates.json (13 pictures of the Hazelmere shoot, copied to candidates/dji/): scripts/parity_jpeg.py candidates/dji --ext .DNG --ev match --lens auto --candidates docs/dji_candidates.json is the regression check for the drone DNGs (their JPEGs are lens-corrected, hence --lens auto); each entry also keeps previous_default, the numbers of the old fixed-lightness rule.
- Full auto: the pipeline's defaults pick the best treatment for each picture by themselves (the tone from the camera JPEG when there is one, the lens correction from the best source there is, the noise clean-up from the picture's own noise and a per-device calibration by ISO); every setting that is not 'auto' (exposure, recover, lens, denoise ...) is for debugging, testing and tuning, and a new behaviour comes with the rule that selects it automatically. Per-device data lives in the profile bundle (`src/stratastills/*_profile.json`, see `inputs.py`): matrices, noise table and its `NoiseScale` (a number or a table over ISO), `LookTable`; lens data comes from the file or from the lensfun database (`scripts/fetch_lensfun.py` -> `models/lensfun/`, CC-BY-SA, not committed).
- Visual report: `scripts/build_report.py` (optional build step: `scripts/setup_env.sh --report`, `setup_env.ps1 -Report`) runs our pipeline stage by stage on the candidate photos (`pipeline.generate(on_stage=...)`) and sets crops from the places where the programs differ most beside the camera JPEG and the darktable/RawTherapee renders in `candidates/renders/`, with the stage settings, into `out/report/index.html` (overviews and crops only, a few MB; `--min-lens N`, `--min-device N`, `--all`, `--stems`). Needs the candidates; never part of CI.
- More candidate sets: `scripts/add_candidates.py <set> <raw files> | --list picks.json` copies raws from anywhere in the archive into `candidates/<set>/` (named `<shoot>_<name>`, with the camera JPEG beside or the one inside the raw) and adds them to `docs/<set>_candidates.json`; sets so far: a7c (every lens: 17), dji, nex5n (7 lenses and a manual one with no lens id), eos60d (Canon CR2), ilce5100. `docs/report_public.json` lists the ones with no person in them (screened with YOLO, then by eye): the report only uses those (the report shows the others too, behind a switch; `--public-only` leaves them out).
- New camera: `scripts/add_device.py <folder with raw+JPG pairs> <candidates.json> --make X --model Y [--noise darktable noiseprofiles.json] [--dcp ...]` builds its profile bundle (matrices, noise table, tone curve, look table, NoiseScale) and the `inputs.PROFILES` entry from its own JPEGs; the sets in the archive are big (nex5n has 124 pictures), the noise fit takes about an hour with `--per-band 8`. Needs the candidates; never part of CI.
- The report is shown by the server too: `/report/` (static files of `settings.report_dir()`, default `out/report`; `GET /api/report` says whether it exists, the web header then links to it). Reached from another machine with `serve --host 0.0.0.0`; no login, trusted networks only.
- On omarchy the app runs as the user service `strata-stills` (port 8362, behind Caddy and the one login at `http://omarchy/strata-stills/`; unit and snippet in dotfiles, see the docs repo's web-proxy job). The web build uses relative asset paths and `BASE` from the page URL (`web/src/api.ts` `withBase`): any new URL the app builds for `fetch`, `<img>` or a link must go through it. A change to the web app needs `npm run build`, a change to Python code `systemctl --user restart strata-stills`.
- The report needs darktable and RawTherapee installed (`externaltools.require()`: `build_report.py`, `render_external.py` and `setup_env --report` stop without them; `stratastills doctor` lists them) and makes any missing render of them itself (`scripts/render_external.py`, with timings kept beside the renders). It shows, per picture, the overview of every program's final picture with switch buttons under it, and the time each program took on this machine; our own stage times and whether each used the GPU come from `rec['timing']` of `pipeline.generate` (`gpu.allocations()`).
- torch: `scripts/setup_torch.py` (run by `setup_env.sh` / `setup_env.ps1`; also on its own after a card change) installs the newest torch the card can run (compute capability under 7.5: torch <2.10 with cu126; newer: cu128; macOS: PyPI; no card: CPU), repairs the cuDNN clash (the CUDA 12 and 13 cuDNN packages share a folder) and probes it; `stratastills doctor` prints SLOW when cuDNN is off. When a package install pulls torch's dependencies, run `scripts/setup_torch.py --check` afterwards.
